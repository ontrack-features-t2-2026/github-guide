# OnTrack T2 2026 setup walkthrough transcript

Companion transcript for the 11 minute 37 second narrated setup walkthrough. The maintained instructions remain `student-setup.md` and `branch-register.md`.

## Set up OnTrack for T2 2026

Welcome. This walkthrough takes a new OnTrack contributor from an empty working folder to a running local development environment and a correctly targeted pull request. It is for the Trimester Two 2026 feature organisation. By the end, you will know which repositories you need, how those repositories fit together, how to select the right objective branch, how to start and initialise OnTrack with Docker, and how to preserve useful evidence for review. Pause whenever a command is on screen. The first Docker build is the slowest part and may take longer than this video. The written student setup guide remains the source of truth, because branch targets can change. Use this recording as a guided companion, then check the branch register before you begin your own ticket.

## 1. Confirm access and prerequisites

Start by accepting your invitation to the ontrack-features-t2-2026 GitHub organisation. Open the Web, API and Deploy repositories in the browser to confirm that your account can read them. If any repository is unavailable, contact the objective lead in the team channel with your GitHub username, the repository name and a screenshot of the error. Do not work around missing access by pushing to an unrelated organisation. Next, read your assigned ticket. Record its identifier, objective, workstream, acceptance criteria, dependencies and which repositories it actually needs. Many tickets affect only one repository. For tools, install Git, Docker Desktop, and Visual Studio Code or another editor. This workflow runs Ruby, Node, MariaDB and Redis inside containers, so you do not need separate host installations of Ruby or Node. Start Docker Desktop before continuing. The containers and image layers use substantial disk space and memory, so close other heavy applications if the first build struggles.

## 2. Keep the repositories together

OnTrack uses three repositories for this workflow. Doubtfire Web is the Angular application that users see. Doubtfire API is the Rails service containing business rules, authorisation, background jobs and data access. Doubtfire Deploy joins them with Docker Compose and the supporting services. Create one parent folder named ontrack-t2-2026, or another name you will recognise. The three repository folders must sit directly beside each other inside that parent. Do not put Web inside Deploy or API inside Web. The local-path Compose file expects sibling directories. Each folder remains an independent Git repository with its own branch, commits and pull request. A ticket may require coordinated changes in more than one repository, but those changes still use separate branches and separate pull requests. Keeping the layout predictable also makes the setup commands and team troubleshooting notes work consistently.

## 3. Clone Deploy, Web and API

Open a terminal. Create the parent folder, move into it, and clone the Deploy repository from the fix slash local-dev-run branch. Then clone Doubtfire Web and Doubtfire API from the same T2 2026 organisation. The full commands are shown on screen and are also available in the written guide for copying. After the downloads finish, verify the origin of each repository. You can run git dash C followed by the folder name and remote dash v. Each origin should point to ontrack-features-t2-2026. If a clone prompts for access, first check that you accepted the organisation invitation and that GitHub authentication is working. Do not paste personal access tokens into chat, screenshots, commands saved in documentation, or pull requests. Do not pull or merge unrelated upstream branches unless your objective lead has asked for that integration. The shared feature branches in this organisation are the operational starting points for these tickets.

## 4. Select the objective branches

Before changing code, open the branch register in the GitHub guide and find the exact current target for your objective. For the Cross-Project Dashboard, the recorded Web and API target is feature slash cross-unit. Email Notifications and Mobile Notifications intentionally share feature slash notifications; the older separate email and mobile branches are not the current target. Peer Progress uses feature slash peer-progress-indicator in both Web and API. Fetch origin, then switch each repository your ticket needs. If Git says a local branch does not exist, use git switch dash dash track origin slash the branch name. The First-Time Tutorial is different. Feature slash student-onboarding is only a proposed name until a repository lead records approval and the exact base commit. Do not create it from this video. Do not create an API or Deploy tutorial branch unless an approved design proves one is necessary. Recheck the branch register whenever you return after several days, because an integration decision can change while your local clone stays the same.

## 5. Start the Docker stack

With the repository branches selected, move into doubtfire-deploy slash development. Confirm Docker Desktop reports that its engine is running. Start the local environment with Docker Compose using docker-compose dot y m l followed by docker-compose dot local-paths dot y m l, then up dash d dash dash build. The local-paths file tells Compose to build from the sibling Web and API folders you just cloned. Detached mode returns control to your terminal while the services continue running. On the first run, Docker downloads base images and installs dependencies, so several quiet minutes can be normal. Use the same two dash f arguments followed by p s to inspect container state. If a build fails because the machine runs out of memory, stop other heavy containers and applications, then retry. Do not delete volumes as a first troubleshooting step; volumes may contain a working local database. Read the error above the final summary because it usually names the actual failed service or command.

## 6. Initialise the local database once

A new clone needs a populated local database. The written guide provides one command that runs the API container temporarily, drops and recreates the development database, loads the schema, sets the Rails environment and runs the standard population task. Copy that command carefully from the guide. It is intentionally destructive to the local development database, so do not point it at a shared or production environment and do not run it merely to repair an unrelated error. In this setup the database is disposable test data, and local account passwords are the standard development password. When population completes, start the services again with the same two Compose files and up dash d. If the database container is still becoming healthy, wait briefly and inspect Compose status or logs. A successful setup has the database, Redis, API and Web services running. Background workers or optional services may also appear depending on the objective branch. Never put real student submissions, grades, feedback, email addresses or other private assessment information into this local demonstration environment.

## 7. Open OnTrack and run a smoke check

Open localhost port forty-two hundred for the Web application and localhost port three thousand slash api slash docs for the API documentation. Sign in with a local development account, not a real user account. The guide lists student underscore one, a tutor, a convenor and an administrator account; the local password is password. First verify that the dashboard loads and that navigation works. Then visit the part of OnTrack related to your ticket. This baseline matters: if something is already broken before your edits, capture it and tell the team rather than accidentally attributing it to your change. Check the browser console and API logs when a screen stays in a loading state. A request that returns an authorisation error is different from a request that never completes. Keep screenshots free of real student information. For feature tickets, plan to repeat the same smoke check after your implementation and at both a normal desktop width and the narrow width named in the acceptance criteria.

## 8. Create a task branch

Now move into the repository required by your ticket. Switch to the objective's shared feature branch, update it with git pull dash dash ff-only origin and the same branch name, then create a separate task branch. A useful naming pattern is workstream slash ticket dash short description. Examples include feature slash A B C one-two-three notification-preferences, docs slash a ticket and topic, security slash a ticket and review, or migration slash a ticket and update. One branch should represent one ticket and one coherent review. Never implement directly on eleven point zero dot x, directly on a shared feature branch, or on a combined validation branch. Before each commit, run git branch dash dash show-current and git status. Stage specific paths rather than every file when your workspace contains unrelated changes. Write a conventional commit message that states the effect, such as feat, fix, docs, test, refactor or chore. Avoid committing generated secrets, environment files, tokens, database dumps, screenshots with private data, or editor-specific clutter.

## 9. Test and preserve evidence

Test in proportion to the change and follow every check named by the ticket. Start with focused tests so failures are easy to diagnose, then run the wider suite, type checking, linting and production build when the acceptance criteria require them. API changes may also need Rails model, service, request and background-job tests plus a Zeitwerk check. Record the exact command, commit, run count and failure count rather than writing only that tests passed. For security-sensitive work, test a permitted user and a denied user, cross-account isolation, malformed input, safe error messages and the absence of private fields. Notification content should minimise lock-screen and email exposure. Peer aggregate data must not reveal identities, raw cohort sizes, marks, feedback or rankings. Dashboard data must remain limited to authorised projects. Use synthetic local data in screenshots. Capture both the normal state and meaningful empty, suppressed, denied or failure states. If a check cannot run because of a real environment limit, keep the log, state the limit precisely and do not convert that result into a pass.

## 10. Push and open the pull request

When the branch is ready to share, push it to origin with dash u so later pushes use the same destination. Open GitHub and choose Compare and pull request. The head is your task branch. The base must be the objective's shared feature branch from which you started. For a notifications example, that base is feature slash notifications. Do not send an ordinary student ticket directly to eleven point zero dot x, and do not target a combined integration or evidence branch. Open the pull request as a Draft if implementation, evidence or testing is incomplete. Use the repository's pull request template. Explain the ticket and scope, what changed, why the approach is safe, exact validation commands and results, screenshots or recordings, related branches or pull requests, and known limits. Link the ticket without copying private board content. A reviewer should be able to reproduce the result without private knowledge or local files that were never committed. Keep authorship and attribution accurate when you build on another contributor's branch or advice.

## 11. Review, handover and troubleshooting

Request at least two useful peer reviews unless the objective's recorded process says otherwise. A reviewer should read the ticket, inspect the changed files, run or assess the relevant checks, consider privacy and authorisation, and leave a clear conclusion. Respond to review comments on the same branch so the pull request retains the full discussion and updates automatically. In the ticket, link the branch, commits, pull request, test output, screenshots, reviewer feedback and final merge. Separate completed, in-progress, planned and deferred work so the handover does not overclaim. For troubleshooting, first confirm you are in the correct folder and branch, Docker Desktop is running, origins point to the T2 organisation, the three repositories are siblings, and the required containers are healthy. Inspect the service logs before rebuilding everything. If branch ownership, tutorial approval, access, or a shared surface is unclear, stop before creating a competing branch and ask in the team channel. The written setup guide and branch register are the maintainable sources. This video is the guided overview. You are now ready to choose your ticket branch, run OnTrack locally, make a focused change, validate it and hand it over safely.
